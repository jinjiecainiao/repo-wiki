# Wiki Writing Rules

## Goal

These rules define the default writing standard for all wiki documents generated by `repo-wiki`.

The generated docs should help a newcomer understand:
- what the project does
- how the repository is organized
- how modules relate to each other
- what to read first
- where the important implementation lives

---

## Language Rules

1. Write all narrative text in the user-selected target language.
2. Keep code symbols unchanged:
   - file paths
   - directory names
   - class names
   - function names
   - package names
   - CLI commands
3. If a term has no good translation, keep the original English term and explain it in the target language.

---

## Audience Rules

1. Write for a newcomer who has never seen the repository before.
2. Prefer explanation over compression.
3. Do not assume project-specific context unless supported by code or README.
4. Prioritize orientation, boundaries, and relationships over micro-level implementation trivia.

---

## Structure Rules

1. Follow the corresponding template file structure first.
2. Use clear Markdown headings.
3. Prefer short sections with strong labels.
4. Use tables when comparing directories, modules, or responsibilities.
5. Use bullet lists for summaries, entry points, and action items.
6. Use Mermaid diagrams where architecture or learning order is easier to understand visually.

---

## Evidence Rules

1. Base conclusions on repository evidence:
   - README
   - config files
   - source tree
   - imports / dependencies
   - entry files
2. Do not invent architecture claims.
3. If something is inferred rather than explicit, label it clearly, for example:
   - `Inferred from code structure`
   - `Likely responsibility based on file layout`
4. When uncertainty remains, prefer a cautious description over a definitive claim.

---

## Style Rules

1. Be concrete, not generic.
2. Avoid empty phrases like:
   - "handles various things"
   - "contains business logic"
   - "used throughout the system"
3. Replace vague statements with repository-specific observations.
4. Keep paragraphs short.
5. Prefer active voice.
6. Avoid marketing tone.

---

## Directory and Module Documentation Rules

1. Each directory description should answer:
   - what is here
   - why it exists
   - whether it is core or supporting
2. Each module description should answer:
   - what problem this module solves
   - where it sits in the architecture
   - what other modules it depends on
   - what key files a newcomer should inspect first

---

## Architecture Documentation Rules

1. Explain the system from high level to detail.
2. Show both:
   - structural relationships
   - important runtime/data flow if discoverable
3. Distinguish between:
   - entry points
   - core business modules
   - infrastructure/support modules
4. Mention external systems only when the codebase provides evidence.

---

## Learning Path Rules

1. The reading order should reduce cognitive load.
2. Recommend foundations first, high-dependency modules later.
3. Explain why each step comes next.
4. Include concrete files or directories to start from.
5. Mark difficulty honestly.

---

## Output Quality Checklist

Before finalizing a document, verify:
- the template structure is preserved
- no `{{placeholder}}` remains
- the language matches the requested language
- code symbols remain unchanged
- unsupported claims are not presented as facts
- the document is helpful to a newcomer
